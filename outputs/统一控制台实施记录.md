### 2.1 F01 exec 只有 cwd，没有子进程隔离

- **修复要点**：新增可验证的本地隔离运行器 `app/security/sandbox.py`——用 macOS `sandbox-exec` 生成一次性 Seatbelt profile：`(deny default)` → 全局 `deny file-write*` 后只 `allow` **任务工作目录**与**任务私有临时目录**；默认 `deny network*`（含回环）；显式 `deny file-read*` 覆盖 `$HOME` 凭据目录（`.ssh/.aws/.gnupg/.config/.codex/.zcode/.netrc/.pgpass/.docker/.kube/.npmrc/.pypirc`、`$HOME/.env`）与 `workspaces.protected_paths` 受保护根；解释器位于机器人项目内时改为逐项 deny 项目敏感子路径（`app/ data/ runtime/ outputs/ tests/ backups/ .git/ work/ .pytest_cache/ .env config.yaml config.example.yaml bot.db`），保留 `.venv`；profile 里每个路径都先 `os.path.realpath`；解释器自身目录在 deny 之后**重新放行**，保证 `execvp` 可用；落在工作目录内的 deny 项会被移除（用户显式授权优先）。`ExecPolicy.require_sandbox=True`（默认），`sandbox_available()` 为 False 时 `run_command` 直接返回 `exit_code=-1` + `denied_reason`，**绝不退回无隔离执行**。子进程输出改为 `_drain()` **增量有界读取**（边读边计数，超限即标记并终止进程组），不再 `communicate()` 之后再截断。
- **改动文件**：`app/security/sandbox.py`（新增，`SandboxPlan.profile/wrap`、`available/_probe`、`deny_read_paths`、`allow_read_paths`、`prepare_plan`、`write_profile`、`self_check`）、`app/security/exec_policy.py`（`run_command`、`_drain`、`_kill_group`、`SANDBOX_UNAVAILABLE_REASON`、`policy_from_config` 的 `require_sandbox/allow_network`）、`app/workspaces/broker.py::_do_run_command`（把 `acl.protected_roots` 传给沙箱）、`config.example.yaml`（`commands.exec.require_sandbox/allow_network`）。
- **测试**：`tests/test_acceptance_probes.py::test_exec_cannot_write_outside_workspace`（带 `helpers.requires_platform_sandbox()`：没有 Seatbelt 的平台**skip 而不是失败**，因为实现会明确禁用 exec）、`tests/test_remediation_contracts.py::test_exec_is_disabled_when_platform_sandbox_missing`、`::test_isolation_status_is_reported`、`::test_exec_command_side_effects_are_recorded`。
- **结果**：通过。越界哨兵文件保持 `unchanged`；模拟"平台无沙箱"时 `exit_code=-1`、`denied_reason` 含"隔离"、stdout 不含被禁命令的输出。
- **剩余限制**：只在 macOS 有效，**Linux/Windows 上 exec 被禁用**；`sandbox-exec` 已被 Apple 标记 deprecated；沙箱**不降权**（仍是机器人用户身份，无 seccomp/容器）；真实项目的 pytest/构建脚本在 Seatbelt 下是否需要额外放行（如 `~/.cache`）未逐项实测；`(allow process-exec)` 允许沙箱内再启动二进制（仍受同一策略约束）。

### 2.3 F03 search 绕过敏感文件和受保护子目录

- **修复要点**：`list/read/search` 统一走一条安全路径：`_resolve()`（拒绝绝对路径与 `..`、realpath、`is_within(root)`、敏感清单）→ `_authorize()`（实时 ACL + 受保护范围 + 敏感）→ `_open_regular()`（`os.open(O_RDONLY|O_NOFOLLOW)` + `fstat` 确认常规文件 + NUL 判定二进制）；`_iter_files()` 遍历时**完全跳过符号链接**，每个目录/文件逐个复查 `is_sensitive`/`is_protected`/范围；`read` 返回的 `sha256` 直接用刚读到的字节计算，消除"检查-打开-哈希"之间的替换窗口。
- **改动文件**：`app/workspaces/broker.py`（`_resolve`、`_open_regular`、`_iter_files`、`_do_list`、`_do_read`、`_do_search`）。
- **测试**：`tests/test_acceptance_probes.py::test_search_does_not_follow_alias_to_sensitive_file`、`::test_search_rechecks_nested_protected_paths`（同时断言直接 `read` 同一受保护文件也被拒）。
- **结果**：通过（两次 search 的 `hits` 均为空）。
- **剩余限制**：敏感/受保护清单仍是黑名单，新形态凭据需部署方加入 `workspaces.protected_paths`；`search` 的起点若本身是文件，仍会按同一安全路径打开。

### 2.4 F04 备份路径符号链接导致授权目录外写入

- **修复要点**：备份不再写"目标同目录 `<文件名>.bak`"。`ChangeSet._backup()` 写入受控目录（`backup_root`，来自 `workspaces.backup_dir`，默认 `runtime/state/backups`，实际路径 `<backup_dir>/<task_id>/<相对路径把 / 换成 __>.bak`，同名冲突追加 `.1.bak`…最多 50 次）；用 `os.open(..., O_CREAT|O_EXCL|O_NOFOLLOW, 0o600)` 创建，**绝不覆盖已有文件、绝不跟随已有 `.bak` 符号链接**；备份失败即取消该文件写入。
- **改动文件**：`app/workspaces/changes.py`（`ChangeSet.backup_root`、`_backup`、`apply(backup_root=...)`）、`app/workspaces/configurator.py::build_workspace_config`（`WorkspaceConfig.backup_dir`，默认 `project_root()/runtime/state/backups`）、`app/tasks/service.py::_make_broker`/`__init__`（把 `backup_root` 传进 `FileBroker`）、`app/main.py` 装配。
- **测试**：`tests/test_acceptance_probes.py::test_backup_cannot_follow_outside_symlink`；`tests/test_remediation_contracts.py::test_backup_dir_is_configurable`。
- **结果**：通过（外部哨兵保持 `unchanged`）。

### 2.6 F06 规划时的文件版本未被默认强制校验

- **修复要点**：`ChangeSet.add_write/add_delete` **总是**冻结计划期状态——存在则记 `before_hash`（`file_hash`），不存在则 `kind=create` 并记住"计划时不存在"；模型的 `expected_sha256` 退化为"额外的、可选的"校验。提交期 `_apply_write` 复核：`before_hash` 非空但文件消失/哈希变化 → `STATUS_CONFLICT` 且不写入；`before_hash` 为空但目标在提交前出现 → `STATUS_CONFLICT`（**不覆盖别人的新文件**）；`_apply_delete` 复核文件仍在且哈希未变，否则冲突。冲突状态**保留为 `conflict`，不降级为 `failed`**。
- **改动文件**：`app/workspaces/changes.py`（`add_write`、`add_delete`、`apply`、`_apply_write`、`_apply_delete`）。
- **测试**：`tests/test_acceptance_probes.py::test_staged_write_detects_changes_without_optional_model_hash`；`tests/test_remediation_contracts.py::test_new_file_created_by_someone_else_is_not_overwritten`、`::test_delete_detects_version_drift`。
- **结果**：通过（并发编辑/新建/删除三种路径都被拒绝写入并保留用户内容）。
- **剩余限制**：哈希是"内容级"的，不做文件锁；提交窗口内的极短竞态由"提交前复核 + 原子 `os.replace`"缩小但不消灭（无法对任意用户进程加锁）。

### 2.7 F07 文件提交全部失败却标记 succeeded

### 4.2 旧目录字段的保守迁移规则（已实测；整改轮收紧）

| 旧字段 | 成员模式 | 管理员模式 | 实现 |
|---|---|---|---|
| `FILE_READ_ROOT` | **无**（整改轮从 `read` 收紧为无） | `read` | `_legacy_grants()`：旧 `/read` 是**管理员命令**，迁移不得把管理员专属能力给普通成员（F09） |
| `FILE_WRITE_ROOT` | 无 | `read, edit` | 历史上只有管理员能写，成员保持无权限 |
| `CODEX_ALLOWED_ROOTS`（每个根） | 无 | `read, edit, exec` | 旧行为是"管理员可读写并执行" |
| `ZCODE_WORKSPACE_ROOT` | 无 | `read, edit` | 旧行为是"管理员可读写" |

**实测（用生产 `.env` 只读构建配置，未打印任何路径）**：迁移得到 4 个授权根、5 条受保护范围、6 条配置说明；`edit_enabled=true`、`exec_enabled=true`、`max_workers=1`。
说明：迁移**不会**把只读根变成可写根，也**不会**给普通成员任何新权限；成员要读必须由用户在 `workspaces.roots[].users` 显式声明（F09 后语义）。
`max_workers` 与 `cross_process_lock`：`build_workspace_config()` 每次启动调用 `enforce_worker_policy()`，`max_workers>1` 或 `cross_process_lock=true` 都会直接报错（F15）。

### 4.3 新旧冲突时的行为与提示位置

- 行为：`workspaces.roots` 存在 → 只用它；同时把每条被忽略的旧字段、其迁移后本应得到的授权逐条列出（"新配置生效、旧字段被忽略，请迁移后删除"）。
- 提示位置：① 启动日志（`app/main.py` 的 `logger.warning("配置说明：%s", note)`）；② `GET /status` 的 `workspaces.notes` 与 `config_notes`；③ `workspaces.roots` 与旧字段并存时还会提示"请迁移后删除，避免两套权限来源并存"。
- 后端侧同理：新式 `backends:` 与旧 per-agent 字段并存时列出受影响的旧字段名（密钥值只显示"（已设置，值不展示）"）。

### 4.4 环境变量优先级与凭据链路

优先级保持并强化为：**真实环境变量 > `.env` > YAML**。

- `load_settings()` 先 `read_env_file(ENV_FILE or ".env")` 拿到 `.env` 的**键名集合**，再 `apply_yaml_config(config_file, skip=frozenset(env_values))`——YAML 只 `setdefault` 注入"环境变量与 `.env` 都没有"的键，不再悄悄盖住 `.env`。
- `.env` 由 pydantic-settings 读入 `Settings`（不会写回 `os.environ`）。因此后端工厂不能只看进程环境：`BackendRegistry._credential_map(settings)` 把三个旧式密钥字段**以及 `.env` 中声明的任意键**（`read_env_file()`）映射成 `BackendConfig.credentials`，`BackendConfig.env()` 的顺序是"进程环境变量 → Settings/.env → YAML 值"。因此自定义 `credential_env`（例如 `CORP_LLM_KEY`）只写在 `.env` 里同样生效。
- **这是本轮修掉的一个真实缺陷**：改造中途的版本里 `BackendConfig.env()` 只读 `os.environ`，导致"密钥只写在 `.env`、进程环境没有该变量"的既有部署（本项目 README 记录的启动方式就是 `.venv/bin/python -m app.main`）会被判定为未配置。
- **实测（修复后）**：仅凭生产 `.env` 构建注册表 → `deepseek_harness`、`zcode`、`codex` 均 `configured=true`；`glm_api`、`gpt_api` 因旧配置里未启用/无密钥而为 `false`（`glm`、`gpt` 两个 Agent 因此显示未配置）。
- 覆盖范围：`.env` 里出现的任意键都会进入映射，因此自定义 `credential_env`（例如 `CORP_LLM_KEY`）只写在 `.env` 也能生效；若密钥放在 systemd/launchd 的环境里，则走 `os.environ`（优先级更高）。回归用例：`tests/test_config_migration.py::test_credentials_from_settings_are_used_when_env_missing`。
- 相关新增测试：`tests/test_config_migration.py::test_credentials_from_settings_are_used_when_env_missing`、`::test_process_env_still_wins_over_settings`、`::test_missing_credentials_report_unavailable`、`::test_env_file_not_modified_by_settings_loading`。

### 5.4 WAL 一致性备份与回滚步骤

- 数据库：`bot.db.consistent-backup`（90112 字节；用 SQLite 一致性方式导出，实测 `PRAGMA integrity_check` = `ok`；单文件自包含，不含 `-wal`/`-shm`）

```bash
# 方式 A：sqlite3 在线备份 API（推荐，服务运行中也可）
sqlite3 data/bot.db ".backup '/tmp/bot.db.$(date +%Y%m%d-%H%M%S)'"

# 方式 B：先 checkpoint 再复制（需能连上数据库）
sqlite3 data/bot.db "PRAGMA wal_checkpoint(TRUNCATE);"
cp data/bot.db /tmp/bot.db.copy

# 方式 C：停服务后连同 WAL/SHM 一起复制
cp data/bot.db data/bot.db-wal data/bot.db-shm /tmp/
```

恢复（回滚到备份点）：

```bash
# 1) 停服务（确保没有进程写库）
# 2) 覆盖主库，并清掉旧 WAL/SHM（否则会与主库不一致）
cp backups/pre-unified-console-20261010-151327/bot.db.consistent-backup data/bot.db
rm -f data/bot.db-wal data/bot.db-shm
# 3) 启动后核对表结构与行数（见 §8.4 检查项）
```

## 7. 风险与缓解

| # | 风险 | 真实性 | 缓解 / 回滚 |
|---|---|---|---|
| R0 | **exec 现在依赖平台沙箱**：macOS 之外（Linux/Windows）没有等价实现，`require_sandbox=true`（默认）时 exec 会被**明确禁用** | 已实现（`app/security/sandbox.py::available` + `ExecPolicy.require_sandbox`） | 部署到非 macOS 前先确认 `exec_policy.isolation_status()`；不要在非 macOS 上把 `require_sandbox` 改成 `false` 来"恢复功能"（那等于放弃隔离）；需要跨平台 exec 应改用容器/受限用户方案 |
| R1 | **team/多文件步骤可能出现部分写入**：`ChangeSet` 逐文件提交，失败、取消或进程被杀都会留下"写了一半"的目录 | 已实现的行为（`changes.py` 明确不承诺整体原子回滚） | 逐文件记录 `status/error/backup`；提交有关键失败时任务**如实失败**（`commit_failed`）并保留完整变更清单（F07）；`/task result` 与 `/team result` 显示清单与备份名；retry 对"已部分写入"的步骤要求 `/confirm` 才重跑 |
| R1a | **备份目录变化**：备份不再写目标同目录 `<文件名>.bak`，改为 `<backup_dir>/<task_id>/…`（默认 `runtime/state/backups/`） | 已实现（F04） | 备份目录需要可写且**不要**放进 `workspaces.roots`（它在默认受保护范围内）；`/task result` 显示备份文件名，恢复时按 §8.3 复制回原路径；旧部署里遗留的 `<文件名>.bak` 文件不会被程序读取或覆盖 |
| R2 | **原生 exec / 原生文件工具默认关闭**：`native_tools` 必须显式开启，且只有 `isolation=sandbox` 的后端可用；实测（生产配置）`native_tools` 未设置 → 全部走 broker | 已实现并实测 | 想开启必须先在真实后端验证隔离；开启后 exec 仍只来自 broker 的 `run_command`（受沙箱 + ExecPolicy 双重约束），不会因为开启原生工具就获得"任意 shell" |
| R3 | **目录锁只保证单进程**：多 worker / 多副本会并发写同一目录 | 已实现（`enforce_worker_policy` **无条件**拒绝 `max_workers>1`，并拒绝 `cross_process_lock=true`） | 保持 `workspaces.max_workers: 1`；需要多 worker 必须先真正实现并验证跨进程锁（当前**未实现**），单靠布尔开关不再能启动 |
| R4 | **确认码在内存里，重启即失效** | 已实现（`InMemoryConfirmationStore`） | 重启后重新发起 `/workspace find` 或操作；TTL 到期同样失效；多进程部署不共享确认码 |
| R5 | **模型不遵守 JSON 协议**：返回散文、坏 JSON、未知动作 | 已实现（`bad_actions` / fatal） | 任务明确失败、不执行自由文本、不产生文件副作用；协议提示词写在 `broker_loop.BROKER_PROTOCOL_PROMPT`；可用 `commands.broker.max_rounds` 调整轮数、`max_task_seconds` 控制总时长 |

mv app /tmp/app.unified-console.$(date +%Y%m%d-%H%M%S)

cp backups/pre-unified-console-20261010-151327/config.example.yaml ./config.example.yaml

还原后：`app/routing/commands.py`、`app/security/file_access.py`、`app/security/tool_policy.py` 回来，
`app/commands/`、`app/workspaces/`、`app/backends/`、`app/tasks/`、`app/api/` 目录不再存在（旧代码不引用它们，可一并删除或留着不管）。

### 8.2 配置回滚

- **生产 `.env` 本轮未改**（首轮与整改轮的时间戳/哈希都与备份一致），通常**不需要**回滚。若部署时改过，用备份里的 `.env` 覆盖前请先核对差异。
- 若部署时新增了 `config.yaml`（新式结构）：删掉它并去掉 `CONFIG_FILE` 即回到纯环境变量 + `.env` 模式；旧式 per-agent 字段在改造前后都能被识别。
- 目录权限回滚：旧代码只认 `FILE_READ_ROOT`/`FILE_WRITE_ROOT`/`CODEX_ALLOWED_ROOTS`/`ZCODE_WORKSPACE_ROOT`。如果部署时已经把这些迁到 `workspaces.roots` 并删掉旧字段，回滚代码前应把旧字段填回去（否则旧代码会认为"没有任何授权目录"）。
- **整改轮新增配置项的回滚**：`workspaces.backup_dir`、`commands.exec.require_sandbox/allow_network`、`commands.broker.max_task_seconds/max_search_entries`、`tasks.effort_set` 相关行为都只在新代码里生效；回滚到首版代码时这些键会被忽略（首版不读取），不会造成启动失败。注意：**回滚到首版代码会失去 exec 沙箱**（首版没有 `app/security/sandbox.py`），首版的 exec 只有 cwd/白名单隔离，这正是被 Codex F01 否决的行为——如需保留隔离，不要回滚这些文件。
- `workspaces.max_workers`/`cross_process_lock`：首版允许"`max_workers>1` + `cross_process_lock: true`"通过自检，整改版一律拒绝。回滚代码后若沿用整改版的配置（`max_workers: 1`）不受影响。

### 8.3 schema 回滚注意点（**不要删数据**）

- 迁移是**纯加法**（新表 + 新列）。回滚到旧代码时：
  - `tasks`/`task_events`/`workspace_bindings`/`file_changes`/`schema_meta` 这几张新表旧代码根本不查，**留着无害**；
  - `agent_preferences.backend`、`team_steps.mode/backend/workspace/find_keyword`、`team_step_runs.*`（含整改轮的 `input_fingerprint`）、`team_workflows.draft_version`、`tasks.result_text/result_summary/result_hash/effort_set` 这些新列，旧代码的 `SELECT` 都显式列名，**多列不会报错**。
- **旧数据继续可用**：旧 team 冻结快照（缺 `mode/backend/workspace/grant_label`）仍按 `text` 解析，不授予文件权限；旧任务行补 `effort_set=0` = "未显式指定强度"；旧步骤行 `input_fingerprint` 为空 = "无可判定输入"（只读步骤 retry 会更保守地拒绝复用，不会误放行）。
- 因此**推荐做法：只回滚代码，不动 schema**；这样一旦再次升级，历史数据（含新列）都还在。
- 只有在必须回到备份时间点时，才按 §5.4 覆盖 `data/bot.db` 并删除 `-wal`/`-shm`；该操作会**丢失备份点之后的所有新数据**（本机核对时该库只有 18 条上下文消息、0 个人偏好、0 个团队），执行前务必确认。
- 任何时候都不要 `DROP TABLE`/`DELETE FROM` 来"回滚 schema"。
- 备份额外注意：整改后的备份文件在 `runtime/state/backups/<task_id>/`（或自定义 `workspaces.backup_dir`），回滚 schema/代码都**不要删除**这些文件；它们是文件级恢复的唯一依据。
